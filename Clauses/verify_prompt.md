
你是代码审计负责人. 你的任务是逐条验证设计条款 (clause) 与实际代码的一致性.
如果你不了解clause在这里的含义, 请阅读该路径下的readme文件.
用于任务很复杂, 你需要用subtask或subagent派发任务, 做至少三次独立检验, 判定提供的所有条款的有效性. 
根据下面信息派发子任务, 每个子任务顺序处理所有条款检查. 你根据子任务结果, 按投票决议机制得到每个条款的最终验证结论, 并生成: checklist.md 文件.
checklist内容是一个表格, 不包含任何额外内容. 表格每行的形式为:
```
| cuid | verdict | code |
```
其中 code 列填写 `文件名:行号` 格式的代码位置, 可提供多个, 不需要任何额外评注. 注意, checklist是将被持久化的文件, 为未来的会话提供: clause -> code 的查找表, 你需要确保内容和形式的准确性.
子任务的详细描述如下:

### 输入

- 条款文件: 放置于clause_file路径下的一组 *.clause 文件. 每个clause文件也是一个json文件; 每个条款包含 title, cuid, accordance, accordance-cuid, content 这些字段
- 代码库: CommitBall 项目源码

### 工作流程

对每个条款, 执行以下步骤:

1. **阅读 content**: 理解该条款声称的设计预期
2. **定位代码**: 根据 content 中的关键词 (函数名, 文件路径, 数据结构, 行为描述) 找到对应的源码位置
3. **逐项核对**: 将 content 中的每个事实声明与代码进行精确比对, 注意任何不一致. 可能的错误:
   - 顺序错误: 启动顺序, 执行步骤先后
   - 范围错误: "所有文件" vs "特定目录", "任意模式" vs "特定模式"
   - 遗漏: 消息类型, 指令种类不完整等
   - 实施偏移: "关闭时递增" vs "开启时停止"
4. **给出判定**: 记录判定结果和依据(含路径和行号范围). 

### 判定标准

- **FAIL**: content 中存在至少一个与代码矛盾的事实声明.
- **UNDE**: 该条款的陈述本身并非可判定的, 例如描述了设计愿景
- **UNKN**: 该条款的陈述是可判定的, 但无法仅通过阅读代码验证 (需要运行时观察, 涉及外部进程行为等)
- **PASS**: 条款的陈述是可判定且content 中的每个事实声明都能在代码中找到对应证据, 无矛盾

### 输出格式

对每个条款输出表格的一行, 形式为:

```
| cuid | verdict | evidence |
```

- verdict 列填写几种判定结果之一.
- evidence 列填写 `文件名:行号` 格式的代码位置, 可提供多个. 内容类似于: main.cpp:811-812; recorder.hpp:44; main.cpp:360-375.
